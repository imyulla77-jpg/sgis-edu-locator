## 6. 배운 점 & 개선 제안

### 6.1 잘된 것 (계속할 것)

- **자동 검증 도구**: `scripts/check-sample.ts`로 무작위 점검하는 것이 버그를 조기에 잡았음 (Act-1에서 F1 발견). 다음 사이클에도 적용할 것
- **설계 문서의 구체성**: DESIGN.md에 "데이터 모양" "영역 판단 규칙" 등 구체적으로 적으니 구현 중 판단 실수가 줄어들었음
- **소규모 API 설계**: 2개 API(`/menus`, `/collect`)로 간결하게 유지해서 이해·테스트·문제 해결이 쉬웠음
- **개발 중 실제 사이트 점검**: iframe·자리표시 같은 예상 밖 문제를 PC에서 즉시 대응 가능했음

### 6.2 어려웠던 점 (개선할 것)

- **브라우저 조종의 예측 불가능성**: "모든 요청 멈춤" 신호가 사이트 구조에 따라 안 나올 수 있음. 다음에는 더 보수적인 대기 규칙(예: 최대값 우선 설정)을 기본값으로 설정
- **실패 이유 기록의 수동 정리**: 처음에는 기술 오류 메시지를 버렸다가 복구하는 식으로 진행됨. DESIGN에서 "오류 처리" 섹션을 더 자세히 적으면 좋음
- **정규식으로 DOM 패턴 판단의 한계**: 요소 이름이나 클래스로 영역을 판단하다 보니 "header"를 어느 정도 포함되면 "상단"인지 기준이 모호했음. DESIGN에 예시(예: `subHeader` → 상단 O, `mainContent-header` → 상단 O)를 명시했으면 처음부터 맞춰졌을 것
- **문장 구조의 예상 밖 조합**: `<br>` 이나 flex 컨테이너 안의 inline-block 같은 웹 기술 조합이 의도와 다르게 글자를 분리했음. DESIGN의 "문구 정리 규칙"에 흔한 함정들을 나열했으면 좋음

### 6.3 다음에 적용할 것

- **"예상 밖" 목록 미리 만들기**: 새로운 사이트나 기능을 다룰 때 "이런 경우에는?" 체크리스트를 Plan 단계에서 미리 만들 것
- **자동 검증을 Plan에 포함하기**: "누가 어떻게 점검할까"를 설계 단계에서 명시해서, 코드에 검증 도구를 먼저 만들 것
- **오류 메시지를 설계하는 것처럼**: 기술 오류(로그)와 사용자 오류(안내)를 DESIGN 단계에서 분리 명시. "사용자 오류는 한글 안내, 기술 오류는 로그에만"처럼
- **웹 표준 함정 문서 만들기**: 이번 사이클에서 마주친 iframe·자리표시·flex 레이아웃 같은 항목들을 팀 위키에 기록해서 다른 기능 개발 때 참고
